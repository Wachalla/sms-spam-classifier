# SMS Spam Classifier

> I first built this in 2024 as a university project. I rebuilt and published it in 2026
> while properly learning Git. Later I re-checked my own evaluation and found a problem.
> This README describes what I found and how I fixed it.

This is a Naive Bayes classifier (a simple model that scores each word by how often it
shows up in spam versus ham) that sorts SMS messages into spam and ham (ham means a
normal, wanted message). It is trained on the UCI SMS Spam Collection, a public set of
real text messages that each carry a spam or ham label.

## Reproduce everything

    python -m venv .venv && source .venv/bin/activate
    pip install -r requirements.txt
    python run_all.py
    pytest

`run_all.py` writes every file in `results/` and rebuilds the results table below from
`results/metrics.json`. I don't type any of the numbers in that table by hand.

## Results

Some terms first:

- **Accuracy**: the share of test messages the model labels correctly.
- **Precision** (for spam): of the messages the model calls spam, the share that really are spam.
- **Recall** (for spam): of the real spam messages, the share the model catches.
- **F1**: one number that combines precision and recall. It is only high when both are high.
- **Holdout**: the test set. I set it aside before training and only use it to score the model.
- **Stratified split**: a split where train and test keep the same spam share.
- **Seed**: a fixed starting number for the random shuffle, so every run makes the same split.
- **Baseline**: a model that always says "ham". Most messages are ham, so it already
  scores high on accuracy while catching zero spam. Any real model has to beat it.
- **Cross-validation**: I split the data into five parts. Each part takes one turn as the
  test set while the model trains on the other four. The spread across the five runs
  shows how much the score depends on which messages land in the test set. I report it as
  mean ± standard deviation (a measure of how far the five scores sit from their average).
- **Train/test overlap**: the number of test messages whose exact text also appears in the
  training data. That should be zero.

## What I found when I re-checked this

### The problem

My old README said the pipeline avoided data leakage. Data leakage means information
from the test set sneaks into training, so the test score looks better than it should.

I did one thing right. I fit the vectorizer (the step that turns text into word counts
and decides which words exist) on the training data only.

But I missed something bigger. The dataset contains exact duplicate messages. Some
spam campaigns send the same text many times, and some short ham messages ("Sorry, I'll
call later") repeat. I made a random split, so copies of the same message landed on both sides. The
model got tested partly on messages it had already seen in training.

### How I found it

I counted how many test messages also appear, word for word, in the training set. On
the original split the answer was not zero. The "Before and after" table above shows
the exact count in the "Train/test overlap" column.

While auditing the data I also found a second, smaller problem. The file has one message
per line and no quoting. But pandas reads it by default as if double quotes wrap fields.
A few messages start with a quote mark. So pandas merged some lines into one row and
stripped quote marks from others. That is why my old README had fewer rows than the
file has lines. `results/audit.md` has the counts.

### The fix

1. Read the file with quote handling turned off, so every line becomes exactly one row.
2. Check for label conflicts (the same text with different labels). If any exist, the
   code stops and reports them instead of guessing. There are none in this dataset.
3. Drop exact duplicates, keeping the first copy, before splitting.
4. Split 80/20 with stratification (both sets keep the same spam share).
5. Fit the vectorizer on training data only, as before.
6. Assert that the train/test overlap is zero. `spam_classifier.py` prints the count, and
   every results table shows it.

### Before and after

The "Before and after" table above runs the same model with the same seed three ways:
the original setup, the parser fix alone, and both fixes. Each row shows its sizes and
its overlap count, so you can see where each change comes from.

### What the small change means

The score barely moved. On the original split, the test messages that were exact copies
of training messages scored higher than the unseen ones. But they were a small share of
the test set, so they could only lift the total a little.

So my original score was mostly honest. But that was luck, not design. Nothing in my
code stopped a copy from landing in both sets. With a dataset that has more duplicates,
the same mistake could have inflated the score a lot, and I would not have known.

## A rule I now follow

**Remove duplicates before splitting, and report the train/test overlap count next to
every score.**

## Near-duplicates: flagged, not removed

Some messages are almost the same, for example the same text with different
capitalization or punctuation. I count them by lowercasing, removing punctuation and
collapsing extra spaces, then checking which messages now match. The counts are in
`results/audit.md` and `results/report.md`.

I don't drop these by default. "Almost the same" is a judgment call. Two short replies
like "ok" and "Ok." are fine to treat as one message. Two spam texts that differ only in
a phone number may or may not count as the same message. I would rather report the number
and decide with care than quietly change the data.

## Casebook

`results/casebook.csv` lists every test message the model got wrong, plus every message
where it was unsure (a spam probability between 0.3 and 0.7). The `id` column is the row
number in `data/sms.tsv`, counting from zero. The last three columns (`my_label`,
`reason`, `rule`) are blank on purpose. I fill them in by hand as I review each case.

## How it works

1. `CountVectorizer` turns each message into word counts. It skips common English words
   like "the". It learns its vocabulary from the training set only.
2. Multinomial Naive Bayes learns how often each word shows up in spam and in ham, then
   picks the more likely label for a new message.
3. `spam_classifier.py` trains the model, prints the scores, and saves it.
   `predict.py` loads the saved model so you can type in messages.
   `app.py` is a small web demo (`pip install -r requirements-app.txt`).

Files:

- `common.py`: shared settings (the random seed and split sizes live here), loading, dedupe, split.
- `audit.py`: data checks, written to `results/audit.md`.
- `evaluate.py`: scores, baseline, cross-validation, before/after table, casebook.
- `run_all.py`: runs all of the above and updates this README.
- `tests/`: checks that train and test share no messages, that the vocabulary comes only
  from training data, and that the whole pipeline runs.

## Limits and next steps

- **Near-duplicates.** Some still cross the train/test split. I report the count but
  don't remove them yet. A next step is to group near-duplicates and split by group.
- **One dataset.** All messages come from one collection, gathered years ago, mostly
  from the UK and Singapore. Spam today looks different. These scores say nothing about
  other sources.
- **A small model.** Word counts plus Naive Bayes ignore word order and context. It is a
  good baseline, not a state-of-the-art filter.
- **One split for the headline numbers.** Cross-validation shows the spread, but the
  holdout table comes from a single seed.

## What I learned

- Fitting the vectorizer on training data only is necessary, but it is not enough. You
  also have to check whether the same examples appear on both sides.
- Accuracy alone misleads on imbalanced data. The always-ham baseline scores high and
  catches no spam. Precision and recall per class tell the real story.
- Check how the file is parsed. A default setting can silently change your data.
- Report how many examples each number comes from.
